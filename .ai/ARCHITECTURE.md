# LinuxToys — Architecture

> Companion to `AGENTS.md` (rules) — this document describes *how the project is structured*, not *how to work in it*.

## 1. What LinuxToys is

A cross-distro Linux app installer/manager for **x86-64 and AArch64 hosts**. A curated catalog of **Bash install scripts** (one script per app, plus JSON/metadata, under `p3/scripts/`) is presented through a **PyGObject/GTK3 GUI** (default) or a **Textual TUI** (CLI mode). Execution is mediated by a busy package-manager preflight (`package_guard`), an **architecture policy** (`architecture*.py` — every script, catalog entry, release asset and payload is checked against the host ISA before anything privileged runs), a script-API version gate (`architecture.require_api` — scripts written for a different script API are refused), `askpass`/`sudo_` privilege escalation in the bash core, AUR source-security verification (`aur_security`), a transaction lifecycle (transmap + `term_registry.ExecutionRegistry`), a **git-based script sync** (`git_scripts_manager` + `scripts_loader`, tracking the `psygreg/scripts` mirror's default branch so live script fixes flow without a client release), and an in-app **self-updater** (`updater/`).

Two native Rust components: **`src/catalog-rs`** → `_catalog_rs` is compiled via PyO3/maturin (catalog JSON parsing/repo-name normalization, git-release asset classification; shared with Python through the `_catalog_rs` module; see `dev/git_db.py`), and **`src/gui-rs`** → `liblinuxtoys_gui.so` is a plain cargo cdylib exposing a C ABI consumed by the Python GUI through ctypes (GTK theming helpers).

A self-managed **Nix subsystem** sits alongside those catalogs: when Nix is present, the GUI/TUI expose a Nixpkgs category whose Installed tab lists applied Nix packages and imported flakes, merge matching Nix packages into existing AppStream entries as `Nix (home-manager)`/`Nix (system)` sources, and keep unmatched offers in a separate category ordered last in search. On NixOS hosts, API-categorized packages are folded into the matching LinuxToys categories, and broken/deprecated/unwrapped packages are filtered out by the Rust catalog. On every other host except gregOS, the subsystem enables Home Manager's `targets.genericLinux.gpu` target and runs the generated `non-nixos-gpu-setup` through `sudo_` so Nix applications can use the host GPU stack; Home Manager switch output is captured so its GPU-driver-update warning re-runs the exact reported setup command. Non-NixOS setups also install a weekly cleanup that keeps the newest three generations, removes older generations after two weeks, collects the store and enables store optimisation. NixOS and its derivatives are auto-enabled because Nix is their native package source; on NixOS the subsystem also owns the host features that are system options (Flatpak via `services.flatpak.enable`, AppImages via `programs.appimage.enable`/binfmt) and repository listings are available only through a flake in their git project (git-db `flake` marker), installed by default-package import; on other hosts agents can run the MCP `nix_enable_subsystem` tool to install Nix and prepare the subsystem. The catalog's Nix installer uses distro packages where available — Arch/CachyOS `nix`, and Fedora 43+ `nix` + `nix-daemon` with the daemon enabled — falling back to the upstream installer on the remaining supported hosts. Installs never use `nix-env`: a persistent queue is applied through a LinuxToys-owned `linuxtoys.nix` module imported into home-manager and/or the NixOS configuration (see `nix_catalog.py`, `nix_queue.py`, `nixsys.bash` and `nix.rs`). Applied packages are registered as `Nix: <attr>` Action Registry transactions and imported flakes as `Nix flake: <reference>` transactions (`nix_registry.py`) so both follow the standard removal flow; manifest export turns them into `require:nix`/`require:nix-subsystem` plus an adjacent flake/module bundle, and manifest import prepares the subsystem and applies that bundle (through Home Manager, with NixOS native-to-system conversion). The hamburger/TUI menu can also import an external flake: `nix_flakes.py` pins it in a locked wrapper, discovers its packages, modules, overlays, apps and configurations, and merges the selected outputs through a generated `linuxtoys-flakes.nix` (or `linuxtoys-system-flakes.nix`) module imported by the LinuxToys module — creating a Home Manager or NixOS flake around an existing classic configuration when no flake exists yet. Removing one flake drops only its state record and generated code, cleans unused wrapper trees and rebuilds the affected scope(s); the MCP server exposes dedicated Nix subsystem enablement plus package/flake install, removal and list tools. Card/app-page metadata (logos, localized summaries, screenshots, long descriptions, maintainers, licenses) is enriched on demand from `api.nixsoftware.org` through `nix_metadata.py`.

### ISA policy in one paragraph

`architecture.host()` reads `platform.machine()` and cannot be overridden. `x86_64` keeps the historical release-asset matcher the installed base relies on (architecture-unlabelled assets stay visible/neutral, 32-bit x86 assets rank as last-resort fallback); `aarch64` additionally requires explicit reviewed evidence everywhere. Either way, actual execution is gated by payload inspection (`architecture_files`/`architecture_flatpak`/`architecture_cli`): unknown, foreign or contradictory payloads are refused before privileges, and independent data (fonts) needs explicit `architecture_independent` approval. Packages that legitimately embed foreign-platform binaries (e.g. **LSW-WinBoat**, whose deb/rpm ships Windows VM guest assets and multi-platform `.node` prebuilds, and **Positron**, whose debs/rpms bundle VS Code extension VSIXs that ship multi-platform `.node` prebuilds inside their nested zip members) are admitted only through the explicit `guest` content kind (`pkg_fromfile --guest`): non-Linux/foreign binaries count as inert data there, while native package metadata and host-ISA payload evidence remain mandatory; WinBoat's Arch route installs the AUR-only `winboat-bin` through `pkg_install`'s paru/pamac build behind the AUR preflight. Package-file preflights that were not declared (`pkg_fromfile`/`pkg_fromurl`/`pkg_fromrelease` — the route every local-package install and git-release deb/rpm asset takes, plus `pkg_tarball` for tarball URLs) offer the same `guest` declaration through an explicit user-consent dialog, offered only after a silent guest probe proves the declaration would actually pass; declining or a failing guest contract keeps the plain refusal, a taken consent threads the declaration down (`ARCH_PREFLIGHT_GUEST`) so nested preflights never ask twice, and an explicit `--guest` on `pkg_fromurl --tar` skips the dialog. The tar-slip link guard is scoped to the payloads this application unpacks itself: deb/rpm/Arch files unpack through the native package managers at the filesystem root (declared absolute/`..` link targets are their own domain — rpm was never link-checked), while tarball routes and every nested archive keep the strict guard. Catalog entries outside the reviewed policy (e.g. **Volt**, whose external Flatpak-extension build route is not qualified) are hidden on every ISA until qualified.

**Defaults by entry kind.** Scripts are presumed x86_64-only unless a `# architectures:` header tags them otherwise (aarch64-capable scripts also carry the `# requires-script-api: 1` marker). AppStream native/Flatpak/Snap, Homebrew and Nix entries are self-managed: those sources only offer what the host can use and their installers resolve ISA (AppStream data is per-arch by construction, Flatpak metadata is read from the host-arch directory, brew handles arm64 Linux itself, and nixpkgs evaluates/builds for the host — the Nix snapshot is rejected when its `legacyPackages.<system>` prefix does not match the shared x86_64/aarch64 policy). Repository listings are x86_64-only by presumption: `architecture.require_entry` grants aarch64 at runtime only when `p3/scripts/git-db.json` proves an installable aarch64 asset (explicitly tagged deb/rpm/pacman/appimage for git entries, an explicitly tagged tarball for tar entries, the exact declared asset for bin entries) or the record declares `architectures` explicitly; an asset without architecture evidence, a single-binary asset or a tarball asset never grants ARM. AppStream overlays are likewise x86_64-only by presumption: without an explicit `architectures` list in their record they only apply on x86_64, and an aarch64 host installs the plain app without the overlay's extras. AUR installs are PKGBUILD-checked through the same statically read `arch` array: the native preflight (`architecture_cli`) requires x86_64/any on x86_64 hosts and aarch64/armv8h/any on ARM (`pkgbuild_builds_natively`), and `aur_security` additionally refuses AARCH64-hostile PKGBUILDs with localized findings in the GUI/TUI/MCP pipelines.

## 3. Runtime flow

```
/usr/bin/linuxtoys (launcher, written by each packager; the Nix launcher also
  exports the packaged Python/GTK/typelib/pixbuf environment and LINUXTOYS_LAUNCHER)
  └─> p3/linuxtoys.py            # prepends p3/vendor to sys.path, then runs app package
        └─> p3/app/main.py       # arg/env parsing: EASY_CLI, linuxtoys:// URL, hybrid-GPU...
              ├─> GUI path: main.run() → Gtk.Application + window.AppWindow (PyGObject + liblinuxtoys_gui.so)
              ├─> TUI path: tui/ (Textual app, EASY_CLI=1)
              └─> linuxtoys:// URL / single-script run paths
```

Every script execution — GUI, TUI, CLI, MCP, AppStream or `call_script` nested — funnels through `library_loader.script_command`/`script_preamble`: the ISA gate (`architecture.host()` + `require_script`, including the script-API version gate), hook validation, then the preamble that sources the bash core (whose own first line re-checks the host before anything else runs).

## 4. Module map — Python application (`p3/app`)

#### Architecture & script-integrity policy (cross-cutting, p3/app top-level)

| File | Role |
|---|---|
| `architecture.py` | The single ISA authority (`ArchitectureError(ValueError)`): `host()` from `platform.machine()` only; alias/foreign-token tables (`LABELS`, `_FOREIGN`); microarchitecture-level canonicalization (`variant_appendix`/`canonicalize` — `amd64v3`-style appendix labels and `x86_64_v3`/`znver4`-style level tags fold into the host ISA while keeping the level for display; unknown variants and foreign ISAs are still refused); static PKGBUILD `arch`-array reading for AUR builds (`pkgbuild_architectures` — no network, array never evaluated — shared with `aur_security`, plus `pkgbuild_builds_natively` gating host CARCH/`any`/`armv8h` tokens); release-asset eligibility + three-tier ranking (`asset_eligible`/`select_asset`); script text gate `require_script` (explicit `# architectures:` header, else x86_64 presumption); catalog gate `require_entry` (ISA derived at runtime from the entry's own record — explicit `architectures` marker or `git-db.json` asset evidence — AppStream native/flathub/snap/homebrew and Nix auto-declare the host, and a NixOS repository listing's `nix_flake` marker delegates ISA to the flake evaluation); hook validation `require_overrides`/`resolve_hook_path` (inline hooks are x86_64-only by presumption); script-API version gate `require_api` (`# requires-script-api:` headers — a script written for another API version is refused). |
| `architecture_files.py` | Read-only native payload inspection: ELF header parse, deb/rpm/arch metadata (arch labels canonicalized through `app.architecture` — microarchitecture levels fold into the host ISA), zip/tar/cpio members with nested-archive bounds, `ar` static libraries walked with the same member policy (their ELF relocatable members are machine evidence — an application tarball legitimately ships `libpython*.a` next to its `.so` files — while symbol-index/long-name members are metadata and unknown-format members refuse like any other native-suffixed file), and zstd-compressed members decoded through the installed decoder (Python 3.14+ stdlib, else the `zstd` CLI, else the unqualified refusal) so their bounded decompressed contents are judged exactly like gzip/xz members — concatenated frames and Blender's per-block `.blend` documents included; `.flatpak` single-file bundles qualify through their own ostree delta superblock metadata (`architecture_files.flatpak_bundle_ref` parses the ref via GLib — the ref's arch is the payload evidence, judged with the filename hints so a contradicting name refuses; the contents are content-addressed ostree objects deployed by flatpak/ostree, and `.snap`/`.eopkg` stay unqualified refusals); payload-sized tool output (`dpkg-deb --fsys-tarfile`, `rpm2cpio`, `bsdtar -cf -`) streams through a deadline/size-bounded reader instead of buffering the decompressed payload whole (small metadata queries keep the 256 MiB buffered cap), and the explicit `guest` content kind tolerates declared foreign-platform binaries (VM guest assets, multi-platform prebuilds) as inert data while still requiring native package metadata and host-ISA evidence (guest-tolerated foreign content still conflicts with all/noarch metadata). The tar-slip link guard is scoped to the routes this application unpacks itself: deb/rpm/Arch package files unpack through the native package managers at the filesystem root, so their declared absolute/`..` link targets are the package manager's own domain, while tarball routes and every nested archive keep the strict guard. Declared-source trees must be free of prebuilt binaries (`validate_tree`). Never executes downloads. |
| `architecture_flatpak.py` | Read-only Flatpak ref resolution (`flatpak remote-info --arch=<host>`) and runtime-extension planning from the installed runtime's `[Extension]` metadata — no hardcoded branch lists. |
| `architecture_cli.py` | Subprocess entry point for Bash (`label|script|hook|files|tree|release|packages|snap|flatpak|extension`): the gate `linuxtoys.bash`, `packages.bash` and `install.sh` call. APT plan validation, cache-only native metadata preflights (candidate listings require one native or arch-independent candidate — multilib/multiarch same-name siblings are never selected for a bare name, while rpm arch-qualified names (name.i686) are explicit multilib requests the dnf backend honors on x86_64 hosts, with the metadata gate then requiring the requested label among the candidates; dnf5's concatenated queryformat output is separated by the trailing-newline queryformat; labels are canonicalized before the gate — microarchitecture levels fold into the host ISA; dnf and zypper fall back to one unprivileged metadata-fetching retry (`dnf --assumeyes repoquery` / `zypper --non-interactive info`, mirroring the install paths' own interactivity policy) when a repository the calling script just added has no cached metadata yet; dnf additionally resolves a bare name through one unprivileged `repoquery --whatprovides` when the name query comes up empty, because the install command selects a provider for a virtual Provides (Fedora 45 has no package named `wget` — only `wget1-wget`/`wget2-wget` provide it), with the providers' own arch labels judged by the same gate — a genuinely missing or foreign-ISA package is still refused, and nothing presumes the host ISA; the zypper/eopkg metadata reader matches both `Arch` and `Architecture` line spellings and eopkg's comma-folded `Architecture : x86_64, Installed Size: ...` label is split at the first comma, and eopkg's exit-0 "not found in binary repositories" line is the availability verdict — refused as "{package} is not available from the eopkg repositories"; APT has no unprivileged metadata fetch, so an invisible name is never refused at the listing stage — absence (silent on apt 2.x, "No packages found" on apt 3.x) defers to the simulated installation plan, which carries apt's own reason and still ISA-gates every planned package, and a plan refusal over invisible names gains an actionable cause note distinguishing absent package lists (`_apt_lists_state` reads the configured `Dir::State::lists` for `*Packages*` files) from a package living in a non-enabled component such as Debian's contrib); the `packages` command exits 2 for policy refusals (`_PolicyRefusal`: package options, explicit foreign-ISA requests, unsupported backends — refusals fresh metadata can never cure) and 1 for availability refusals, the contract the install path's metadata-recovery wrappers branch on; snapd metadata queries; `files` carries the `guest` content kind for packages that legitimately embed foreign-platform binaries. For pacman, a target missing from the sync databases is an AUR-only candidate on the pacman-driven arch family (pkg_install routes it to a paru/pamac build; SteamOS-family hosts have no AUR route and keep the refusal): the AUR preflight verifies exact-name existence against the AUR RPC plus the PKGBUILD's statically read `arch` array (`pkgbuild_architectures`/`pkgbuild_builds_natively`) against the host — the RPC exposes no arch field — and refuses anything unavailable, foreign-ISA, or unreadable, fail-closed. |

## 5. Catalog scripts & data (`p3/scripts`)

The catalog is **data, not code**: one `.sh` per app plus JSON/metadata. Headers are machine-parsed (`parser.py`, `scripts.rs`), so their keys are a contract:

- Script header: `# name:`, `# version:`, `# description: <i18n key>`, `# icon:`, plus policy flags — `# compat:` (e.g. `!solus, !ostree`), `# nixos: yes|no` (explicit NixOS opt-in; scripts without it stay hidden there), `# gpu:`, `# hybridgpu:`, `# desktop:`, `# systemd:`, `# wayland:`, `# cpu:`, `# deviceids:`, `# reboot: yes|ostree`, `# revert:`, `# registry:`, `# negates:` (hides other scripts when this one succeeds), `# localize:`, `# nocontainer`, `# gregos-version:`, `# cachyos-mirrors-required: 0` (opts a backend that never consults the distro repositories out of the CachyOS mirror preflight).
- ISA contract: scripts declare ISA support in the tree itself — `# architectures: x86_64[, aarch64]` header — and are **x86_64-only by presumption** otherwise: headerless scripts run on x86_64 and are refused elsewhere. Aarch64-capable scripts must also carry `# requires-script-api: 1`. Local/generated scripts always get an explicit host header. The repository-support scripts under `repos/` are tagged individually per upstream ARM availability (Flathub/FlatPark/Homebrew/Cargo/Nix/Pacstall/Pip/RPM Fusion/Snap/Terra dual; Chaotic-AUR and Multilib are x86_64-only upstream). Visibility propagates through dependencies: when a prerequisite (`# needed:`) or an unconditioned `call_script` target is not offerable on the host, every entry that depends on it is hidden too, even if the dependent itself would be ISA-compatible.
- Live catalog: the tree is mirrored verbatim to `psygreg/scripts`, whose default branch is the client's remote sync source — script fixes flow to installed clients without a client release, and nothing pins content digests on the client side. Aarch64 qualification is likewise explicit in the tree: a script header, a listing record's `architectures` marker, or `git-db.json` release-asset evidence (rebuild with `dev/git_db.py` after releases change). `# requires-script-api: 1` marks scripts that use the managed script API; `architecture.require_api` refuses any other value.
- `category-info.txt` per directory: `ICON:` + `description: <i18n key>`.
- `repos.json` + `lists/*.json`: repository/app entries (source URLs, screenshots, descriptions.json per list with translated long descriptions, hooks under `scripts/lists/<app>/*-pre.sh`/`-post.sh`); git-type repos are resolved via `git-db.json` (built by `dev/git_db.py`).
- `scripts/sysup.sh` + `scripts/sys/` — system-update and driver flows (the update pass also refreshes FUSE 2 installs that came from the Debian-stable package-file fallback through their `fuse2-deb` registry record, comparing the suite's current version against the installed one with dpkg's version ordering; when Nix is available it refreshes flake inputs/channels and rebuilds the NixOS system and/or Home Manager profiles, with the Home Manager rebuild re-running non-NixOS GPU setup when its driver warning appears; on NixOS the native update branch is the NixOS rebuild itself and reboot recommendation compares the booted and current kernels); `scripts/lists/` — upstream hooks.
- i18n: `p3/libs/lang/<code>.json` (app strings, plus the bash-side guard/route refusal strings read by `packages.bash` through jq) + `<code>.lib` (bash message strings — generic `msgNNN`/alias stores plus named per-feature dialog blocks, e.g. the Skills Seeker's `_skills_*` set, each backed by inline English floors in the script itself), ~58 languages.

## 8. Packaging, dev tooling & CI

### Build orchestration

- `build-rust.sh` (root) — `build|develop|release|vendor`. `release` vendors deps, builds+deploys both Rust artifacts, then drives distrobox packagers: fedora→`dev/build/copr/build.sh`, arch→`dev/build/pkg/build.sh` + `dev/build/appimage/build.sh`, ubuntu→`dev/build/deb/build.sh`.
- `flake.nix` + `nix/package.nix` — Nix package and developer shell for x86_64/aarch64 Linux. `packages.<system>.default` builds both Rust crates from the committed `Cargo.lock` with `rustPlatform.buildRustPackage`, installs the `p3/` runtime tree under `share/linuxtoys`, and wraps the launcher with `python312.withPackages` (textual/pyte pins matching `p3/requirements.txt`), GTK/VTE/Pango/AppStream typelibs, a combined gdk-pixbuf loader cache (built-in + SVG + WebP), runtime tools and desktop/MIME/metainfo assets. `nixosModules.default` exposes `programs.linuxtoys.enable`, and `shell.nix` provides the same GTK/Python/Rust toolchain for `nix develop`.
- `dev/build/vendor_deps.sh` — pins textual/pyte from `p3/requirements.txt` into `p3/vendor` (gitignored); refuses to vendor `.so` binaries; `p3/linuxtoys.py` prepends it to `sys.path`.

### Nix flake

`flake.nix` exposes `packages.<system>.default`/`linuxtoys`, `apps.default`, `devShells.default` and `nixosModules.default` for `x86_64-linux` and `aarch64-linux`. `nix/package.nix` is the single build recipe: `rustPlatform.buildRustPackage` compiles both workspace crates offline from `Cargo.lock`, then installs the `p3` tree and the two native libraries. The launcher sets `LINUXTOYS_LAUNCHER` (so the app's generated MCP user unit re-enters the wrapped launcher), the Python/GTK runtime `PATH`, `GI_TYPELIB_PATH` (GTK/GdkPixbuf/Pango/Vte/GLib/librsvg/gobject-introspection/AppStream/Flatpak/HarfBuzz/Atk), `LD_LIBRARY_PATH`, `XDG_DATA_DIRS` and a combined gdk-pixbuf loader cache. The flake's interpreter carries the exact TUI pins instead of a pip-vendored `p3/vendor`. Nix installs are recognized by `update_helper.is_from_repository` (path under `/nix/store`), so the self-updater and outdated-version gate stay inactive; updates arrive through `nix profile upgrade` or the system rebuild.

### CI (`.github/workflows/`)

- `release.yml` — triggers: `workflow_dispatch` (version/upload_ppa/test) or push to master touching `src/ver`. Jobs: `prepare` (version + release notes + `vendor_deps.sh`, uploads `tui-vendor`), `ci-image` (aarch64: fetches the Arch Linux ARM rootfs, verifies its detached signature against ALARM's pinned published key fingerprints, builds `.github/ci-images/archlinux-aarch64/Dockerfile` on the arm runner and pushes it to GHCR — Arch's official images are linux/amd64-only, so the arm legs cannot pull them — and outputs a digest-pinned image reference; the image also disables pacman's download sandbox — Landlock, the syscall filter and the `alpm` privilege drop all fail inside the runner container, the same mitigation Arch's official Docker images ship — initializes the pacman keyring, and normalizes makepkg's `PKGEXT` to Arch's standard `.pkg.tar.zst` (ALARM's makepkg.conf still defaults to `.pkg.tar.xz`, which made the release workflow's package copy step fail on the aarch64 leg)), `deb-ppa`, `rpm` (fedora container), `arch-pkg` (arch container; the aarch64 leg runs the digest-pinned ALARM-based image from `ci-image`), `appimage` (arch container; same aarch64 image), then `release` (sha256sums + `gh release create`). Test mode requires an existing tag; already-tagged push no-ops. Every packaging job runs twice through a native-architecture matrix (x86_64 leg on `ubuntu-24.04`, aarch64 leg on `ubuntu-24.04-arm`, native distro containers — fedora is multi-arch, the Arch aarch64 container is ALARM-based — no emulation/cross toolchains), so the release carries both `amd64`/`x86_64` and `arm64`/`aarch64` assets. Each leg uploads its own `release-assets-<job>-<arch>` artifact; the `.src.rpm` and the AUR tarball + `PKGBUILD` are collected once, from the x86_64 legs, to avoid name collisions in `dist/`. The PPA source upload happens exactly once, from the amd64 deb leg (`build.sh --binary-only` keeps the arm64 deb leg off the PPA); Launchpad can additionally build `arm64` when that arch is enabled on the PPA (`debian/control` declares `Architecture: any`). Local native ARM64 development builds use `dev/build/deb/build.sh --native`.
- `sync-scripts.yml` — push to master touching `p3/scripts/**` mirrors the tree into `psygreg/scripts` (wiping everything but LICENSE/README.md). The synced mirror's default branch is the client's remote sync source; new commits there reach installed clients on the next sync without any tagging step.

### Other tooling

- `dev/git_db.py` — manual (unwired) builder of `p3/scripts/git-db.json`: latest-release assets for every git-type repo plus a `flake` marker from the default branch's repository-root `flake.nix`, arch detection delegated to `app.architecture` (the same policy the runtime uses). `--flakes` refreshes only the flake markers without touching release assets. Consumed by `p3/app/repo_parser.py`, `src/catalog-rs/repo.rs` and the runtime ISA derivation in `architecture.require_entry`.
- `install.sh` (root) — user installer: `_resolve_route()` maps `$ID` (with `$ID_LIKE` as the fallback) to the installation handler and the release-asset kind that handler consumes (the Manjaro-family AUR route consumes none; immutable systems and Solus take the Gear Lever AppImage route); only the route's own asset kind is selected, through the staged architecture validation (`architecture_prepare`/`architecture_verify` gates the host, refuses foreign payloads, and payload-verifies every download). When the host's preferred kind has no native asset in the release (an aarch64 host on an x86-only release) but a verified native AppImage exists, the installer warns explicitly and falls back to the AppImage route; with neither candidate it fails closed. Before the architecture staging, `_lt_repair_gate` resolves the installed state: when the installed version already equals the release tag, a plain reinstall would silently no-op and keep any damage (a third-party package operation that deleted a package-owned file — discussion #1500), so the route's package manager verifies the installation instead — dpkg `--verify` + owned-file existence scan, `rpm -V` (mtime/user/group drift ignored), `pacman -Qkk`, or the AppImage desktop-entry/file discovery — an intact installation exits as "already installed and up to date" (skipping all staging and downloads), a damaged one is reinstalled with repair semantics (`_lt_repair`: apt `--reinstall`, dnf/yum `reinstall`, a removal before the pamac build; the AppImage fallback refuses in repair mode), and older, newer or undetectable installations keep the legacy path. `LINUXTOYS_REINSTALL=1` forces the clean reinstall of an intact same-version installation. NixOS and its derivatives resolve to `osnix` before the API/asset staging: it installs the latest tagged flake (`github:psygreg/linuxtoys/<tag>`, falling back to the default branch for releases predating the flake), runs `nix profile upgrade linuxtoys` on existing profiles, and honors `LINUXTOYS_REINSTALL=1` by removing the profile entry first. Nix store installs are package-manager-owned, so the self-updater and outdated-version gate stay inactive there.
